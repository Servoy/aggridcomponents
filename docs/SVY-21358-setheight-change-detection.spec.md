# Spec: SVY-21358 — [Sablo error] on responsive form with aggrid (setHeight change-detection hardening)

## 1. Goal

Eliminate the aggrid-owned browser error that appears when a **responsive** form
containing a Power Grid or Data Grid is opened:

```
ERROR Error: NG0100: ExpressionChangedAfterItHasBeenCheckedError ...
  at setHeight (nggrid.ts)
  at svyOnChanges ...
  at ngOnChanges ...
  at throwErrorIfNoChangesMode ...
```

`NGGridDirective.setHeight()` mutates `agGridElementRef.nativeElement.style.height`
(and toggles the AG Grid `domLayout` option) synchronously from `svyOnChanges`, which
runs inside Angular's change-detection pass. In dev mode this trips the
`ExpressionChangedAfterItHasBeenChecked` / no-changes assertion when `responsiveHeight`
changes. Harden `setHeight()` so the DOM/style mutation runs **after** the checked
change-detection phase, for **both** grids.

The second error in the ticket — the server-side Sablo `java.awt.Dimension[width=140,height=20]`
serialization failure — is **not** owned by this repository and is explicitly out of
scope for a code change here (see §3.3 and §6). This spec documents the investigation
that confirms this so the finding is not lost.

## 2. Background

The ticket (title tagged `[Sablo error]`, fixVersion 2026.9.0) reports that opening a
responsive form with an aggrid produces console errors. The attached `servoy_log.txt`
contains **two distinct errors**:

1. A server-side Sablo serialization error:
   `ObjectPropertyType.toJSONValue ... unsupported value type:null for value: java.awt.Dimension[width=140,height=20]`.
   Its full stack trace is entirely framework code
   (`org.sablo.specification.property.types.ObjectPropertyType`,
   `com.servoy.j2db.server.ngclient.AngularFormGenerator`,
   `com.servoy.eclipse.designer.editor.rfb.DesignerWebsocketSession`) generated by the
   RFB form designer at design time.
2. A browser `ExpressionChangedAfterItHasBeenChecked` error whose stack frame maps to
   this repo's `NGGridDirective.setHeight()`.

Architect comments on the ticket (Johan Compagner: "i think this should be fixed, but
we can use this case to track down (E2E) failures like this."; Andrei Costescu: "Check
for more similar e2e problems.") indicate the intent is to clean up the error(s)
surfaced by this responsive-form scenario.

User context for this work: *"is there any error that is in the ng grid codebase for this
ticket?"* — Answer confirmed by investigation: **yes, exactly one** — the `setHeight`
change-detection error. That is the error this spec fixes.

### Relevant code

- `aggrid/projects/nggrids/src/nggrid.ts:214` — `NGGridDirective.setHeight()`. Sets
  `agGridElementRef().nativeElement.style.height` and calls
  `agGrid.api.setGridOption('domLayout', ...)` (or mutates `this.agGridOptions.domLayout`).
- `aggrid/projects/nggrids/src/powergrid/powergrid.ts:772` — `svyOnChanges` calls
  `setHeight()` synchronously on the `responsiveHeight` change case.
- `aggrid/projects/nggrids/src/datagrid/datagrid.ts:1230` — same pattern in Data Grid
  `svyOnChanges`.
- `powergrid.ts:611` and `datagrid.ts:962` — `setHeight()` also called once during
  `ngOnInit`/grid setup (before AG Grid API exists). These calls are safe and must keep
  working; the fix must not break them.
- `ServoyBaseComponent` exposes `protected cdRef: ChangeDetectorRef` and
  `protected renderer: Renderer2` (see `@servoy/public` `servoy-public.d.ts:95-96`), and
  a `detectChanges()` helper.

## 3. Design

### 3.1 The change-detection problem

`svyOnChanges` is invoked from `ngOnChanges` (see `ServoyBaseComponent.ngOnChanges`).
`ngOnChanges` runs during Angular's change-detection cycle. When `setHeight()` writes to
`style.height` (or flips `domLayout`) at that moment, it can change a value that Angular
has already checked in the same pass, producing `NG0100`
(`ExpressionChangedAfterItHasBeenChecked`) in dev mode. The `responsiveHeight` input
changing on a responsive form is the trigger observed in the log.

### 3.2 Fix: defer the style mutation out of the checked phase

Keep `setHeight()` correct for its two callers (init-time and change-time), but ensure
that when it is invoked **from `svyOnChanges`** the actual DOM/style write does not run
inside the current change-detection pass.

Preferred approach — defer within `setHeight()` itself so both grids and both call sites
benefit without touching each `svyOnChanges`:

- Wrap the DOM/style mutation portion so it executes after the current CD pass. Use the
  directive's existing `setTimeout` guard helper (`nggrid.ts:121`, which already no-ops
  after destroy) to schedule the write on the next macrotask, OR use Angular
  `afterNextRender` via an injected `Injector` if it is available in the installed
  Angular 22 API surface. `setTimeout` is the lower-risk, already-established pattern in
  this codebase (used pervasively in both grids) and the directive already tracks
  `destroyed` to avoid post-teardown mutations.
- The init-time call (`powergrid.ts:611` / `datagrid.ts:962`) runs before the AG Grid API
  exists and only mutates `this.agGridOptions` (a plain config object), which is not part
  of a checked view expression — deferring it is harmless but not required. Ensure the
  chosen implementation still applies `agGridOptions.domLayout`/initial height correctly
  before the grid is created (i.e. do not defer the branch that writes to
  `this.agGridOptions` when the API is absent, or make deferral a no-op in that case).

Concretely, `setHeight()` should:
- Continue to no-op in absolute layout (`isInAbsoluteLayout()`), unchanged.
- When mutating the live grid (`agGrid?.api` present) — i.e. the change-detection-time
  path from `svyOnChanges` — perform the `style.height` write and `setGridOption` call
  in a deferred callback guarded against destruction.
- When only `this.agGridOptions` exists (init-time, no API yet) — apply synchronously as
  today so the grid is created with the right `domLayout`/height.

An implementation-level split (e.g. a private `applyHeight()` doing the actual work, with
`setHeight()` deciding whether to run it now or defer it) keeps the logic testable.

### 3.3 The Sablo `140x20` Dimension error — investigation result

Investigation confirms this error does **not** originate in nggrids:

- The stack trace is 100% server-side framework code (`org.sablo.*`,
  `com.servoy.j2db.server.ngclient.*`, `com.servoy.eclipse.designer.*`). No
  `aggrid/projects/nggrids` TypeScript frame appears.
- The failing value is `java.awt.Dimension[width=140,height=20]`. The only
  `dimension`-typed properties owned by nggrids specs are:
  - `designsize` — default `{width:400,height:300}`
    (`datasettable.spec:21`, `groupingtable.spec:20`), already tagged
    `{"serveronly": true, "scope": "private"}`.
  - `editFormSize` — default `{width:300,height:200}`
    (`datasettable.spec:549`, `groupingtable.spec:749`).
  Neither default is `140x20`. A repo-wide search finds no `140`/`20` dimension default.
  `140x20` is the Servoy platform's default element size for a newly-created responsive
  element, produced by the framework, not by this package.
- Because `designsize` is already `serveronly`, it is not serialized to the client via the
  normal websocket path — this is the design-time RFB `AngularFormGenerator` path, which
  is framework code.

Conclusion: there is no property or behaviour in nggrids that produces, or can guard
against, the `140x20` `java.awt.Dimension`. The defect is a Sablo/servoy-eclipse
`ObjectPropertyType` serialization issue. No nggrids code change can or should be made
for it. It should be tracked/fixed in the sablo / servoy-eclipse repositories. This spec
does not invent an nggrids change for it. (See §6.)

### 3.4 Affected grids

Both grids call `setHeight()` from `svyOnChanges` on the `responsiveHeight` case
(`powergrid.ts:772`, `datagrid.ts:1230`), and both share `NGGridDirective`. Fixing it in
`nggrid.ts` covers both. Verify both.

## 4. Implementation plan

1. In `aggrid/projects/nggrids/src/nggrid.ts`, refactor `setHeight()` so the live-grid
   DOM/style mutation (the branch where `agGrid?.api` exists) is executed in a deferred,
   destruction-guarded callback (reuse the existing `setTimeout(fn, 0)` helper at
   `nggrid.ts:121`), while the init-time `this.agGridOptions` branch (no API yet) stays
   synchronous so the grid is created with the correct `domLayout`/height.
2. Ensure `setHeight()` still handles all current cases: absolute layout no-op,
   `responsiveHeight < 0` → `autoHeight` + clear inline height, `responsiveHeight > 0`
   → `normal` + `height: Npx`, falsy/0/undefined → `normal` + `height: 100%`.
3. Confirm Power Grid (`powergrid.ts:611`, `:772`) and Data Grid (`datagrid.ts:962`,
   `:1230`) call sites need no changes beyond the shared refactor; adjust only if a call
   site relies on synchronous completion.
4. Add/adjust unit tests (Vitest) for `setHeight()` behaviour on a responsive
   (non-absolute) layout: verify the correct `domLayout` and inline height are applied
   for each `responsiveHeight` case, and that changing `responsiveHeight` via
   `svyOnChanges` no longer mutates the style synchronously within the CD pass. Follow
   AGENTS.md test conventions (explicit vitest imports, `TestBed.createComponent`,
   `setInput`, `ServoyPublicTestingModule`, `NO_ERRORS_SCHEMA`, no `NGGridsModule`).
5. Run `npm run build`, `npm run lint`, and `npm run test_headless` from `aggrid/`.
6. Do **not** change any `.spec` / `_doc.js` files — no model property, handler, or API
   contract changes. Document the Sablo-error finding in the ticket/PR description so it
   can be re-routed to sablo/servoy-eclipse.

## 5. Acceptance criteria

- [ ] Opening a responsive form containing a Power Grid no longer logs
      `ExpressionChangedAfterItHasBeenChecked` from `setHeight` when `responsiveHeight`
      changes (dev mode).
- [ ] Same verified for Data Grid.
- [ ] Grid height still renders correctly for all `responsiveHeight` cases: negative
      (autoHeight), positive (fixed px), and 0/undefined (100% of parent).
- [ ] Init-time grid creation still applies the correct `domLayout`/height before the
      AG Grid API exists (no regression from the SVY-22437 `agGridOptions` guard).
- [ ] `npm run build` succeeds; `npm run lint` shows no new warnings; Vitest tests pass.
- [ ] No `.spec` / `_doc.js` contract changes; spec/Angular alignment unchanged.
- [ ] PR/ticket clearly records that the `java.awt.Dimension[140x20]` Sablo error is a
      framework (sablo/servoy-eclipse) serialization defect, not fixable in nggrids.

## 6. Out of scope

- The server-side Sablo `ObjectPropertyType.toJSONValue` `java.awt.Dimension[140x20]`
  serialization error. Investigation (§3.3) confirms it does not originate in and cannot
  be guarded by nggrids code; it belongs to sablo / servoy-eclipse. No code change is
  made here for it — only documentation of the finding.
- Any change to `designsize` / `editFormSize` spec definitions or their defaults.
- Broader zoneless / OnPush migration work beyond what is needed to defer this one
  style mutation.
- AngularJS `datasettable` / `groupingtable` legacy files (the error is Angular-only).
